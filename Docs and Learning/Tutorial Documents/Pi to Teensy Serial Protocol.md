# The Pi-to-Teensy Serial Protocol

**Concept:** what a message protocol is, what choices go into one, and the specific protocol proposed for talking between the Raspberry Pi and the Teensy 4.1.

**Status:** this is a *proposal* built from the existing Dollar Eater protocol. Nothing is implemented yet.

## The general idea

A protocol answers four questions:

1. **Transport:** what carries the bytes?
2. **Framing:** where does one message end and the next begin?
3. **Encoding:** how are values written (text, binary)?
4. **Semantics:** what does each message mean, and what must happen in response?

## Our answers

**Transport.** USB cable from the Pi to the Teensy. The Teensy's `Serial` is native USB, so it appears on the Pi as a serial device (usually `/dev/ttyACM0`). The baud rate is ignored by the Teensy, but we keep 115200 on the Pi so the existing `serial_port.cpp` works for both the Teensy and the Arduino.

**Framing.** One message per ASCII line, ended by `\n` (`\r` tolerated). Fields are separated by single spaces; the first word is the command name. Lines are short (about 40 characters at most); longer lines are rejected with `ERR`.

**Encoding.** Text. Why: easy to type into a serial monitor, easy to log, easy to test with no Pi. Bandwidth is not a concern (see *Serial Link Performance*).

**Semantics.**

Teensy to Pi (events):

| Message | Meaning | Sent when |
|---|---|---|
| `READY <version>` | Booted, outputs in safe state | Boot/reset |
| `BTN <id> <0\|1>` | Button 0-9; 1 = pressed | Debounced state changes |
| `HALL <id> <0\|1>` | Hall sensor 0-3 | Debounced state changes |
| `SLIDER <id> <v>` | Slider 0-1, value 0-1023 | Value moves past deadband, at most every 20 ms |
| `OK <echo>` | Command accepted | After a valid command (skip for high-rate ones like `LED`) |
| `DONE <kind> <id>` | A timed run ended | Timer expires |
| `ERR <text>` | Bad or unknown command | Any rejection |

Pi to Teensy (commands):

| Message | Effect |
|---|---|
| `MOTOR <id> <speed> <ms>` | DC motor 0-3, speed -255..255 |
| `ACT <id> <speed> <ms>` | Linear actuator 0-1 |
| `SOL <id> <ms>` | Pulse solenoid 0-3 |
| `LED <id> <r> <g> <b>` | Button LED 0-9 colour |
| `STRIP <r> <g> <b>` | Strip fill (add effects as needed) |
| `STEP <id> <steps> <rate>` | Move stepper 0-1 by signed steps |
| `ENABLE <0\|1>` | Shared stepper enable |
| `PING` | Keep-alive for the watchdog |
| `SNAPSHOT` | Report every input once (proposed) |
| `STOP` | Everything to a safe state now |

`BTN` and `MOTOR` deliberately match the existing `ButtonEvent.msg` and `MotorCommand.msg`.

## Rules that make it behave

- **Events only on change.** The Pi never polls; it remembers the last value.
- **Idempotent state commands.** Sending `LED 3 255 0 0` twice is the same as once. A new timed command for a device replaces the running one (as `MotorCommand.msg` already says).
- **The Teensy enforces limits.** `MOTOR 0 255 60000` is clamped to the firmware's maximum run time. The Pi can't override safety caps.
- **`DONE` is the completion signal.** The brain never guesses when a run ended. It names the device (`DONE MOTOR 2`) because several can run.
- **Timestamps come from the Pi.** The Teensy doesn't know the time; the Pi node stamps events on arrival (as in `ButtonEvent.msg`'s `stamp`).

## Example

```
Teensy: READY 1
Pi:     LED 4 0 0 255          Teensy: OK LED 4 0 0 255
Teensy: BTN 4 1               (button pressed)
Teensy: BTN 4 0
Pi:     SOL 2 80              Teensy: OK SOL 2 80
Teensy: DONE SOL 2            (80 ms later)
```

## Open questions to decide

1. Add `SNAPSHOT` and make the Pi resend its cached state on every `READY` (recommended; see *Layering the Hardware Interface*).
2. Which commands get an `OK`.
3. Whether any command needs a request ID. Probably not if each device has at most one timed command at a time.
4. Whether `DONE` should become a ROS action result or a topic.
