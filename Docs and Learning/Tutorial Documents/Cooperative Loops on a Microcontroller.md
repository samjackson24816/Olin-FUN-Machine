# Cooperative Loops on a Microcontroller

**Concept:** how one `loop()` can do many jobs "at once" without an operating system, and what limits it.

## The general idea

A microcontroller sketch has no scheduler. `loop()` runs over and over. If one step in it waits, everything else waits.

- **Blocking** code stops the loop until something finishes (`delay(3000)`, waiting for a serial reply, a long I2C transfer).
- **Non-blocking** (cooperative) code remembers *when* something started and checks the clock on each pass:

```cpp
if (running && millis() - startMs >= durationMs) stopMotor();
```

Each job becomes a small `update()` function that does a tiny amount of work and returns. `loop()` just calls every `update()` in turn. The classic reference is Arduino's *Blink Without Delay* example.

**Rollover-safe time math.** `millis()` wraps after ~49 days. Always write `now - start >= duration` (unsigned subtraction survives the wrap). Never write `now >= start + duration`.

**The golden rule:** the loop is only as responsive as its *longest* single pass. Responsiveness = worst-case loop time, not average.

## When a plain loop isn't enough

| Need | Tool | Why |
|---|---|---|
| Steady pulses at a precise rate (stepper STEP) | Hardware timer, e.g. Teensy `IntervalTimer` | The loop can't guarantee timing; a timer interrupt can |
| Long transfers without CPU time (LED strips) | DMA (e.g. `OctoWS2812`) | The hardware shifts data out while the loop keeps running |
| Waiting on a slow device | State machine across loop passes | Start, return, check again later |

Interrupt routines must be short, and variables shared with `loop()` must be `volatile` (and sometimes protected while read).

## How this applies to our project

The Dollar Eater firmware (`firmware/dollar_eater/dollar_eater.ino`) already follows this pattern: `updateSerial()`, `updateSwitch()`, `updateMotor()` called from `loop()`, with the motor stopped by a timer check instead of `delay()`.

The Teensy firmware scales that to many devices:

```
loop():
  readSerialCommands()
  updateInputs()      // 10 buttons, 4 Hall sensors, 2 sliders
  updateOutputs()     // timed motors, actuators, solenoids, LED fades
  checkHostWatchdog()
```

Devices of the same kind live in arrays of structs (`motors[4]`, `buttons[10]`), so there is one `update` loop per type instead of four copies of the same code.

**Our worst-case blocking operations** (estimates from bus arithmetic; measure them):

| Operation | Blocks for |
|---|---|
| I2C write, one LED (3 channels) | ~0.3 ms at 400 kHz |
| I2C write, all 30 LED channels | ~2.8 ms |
| WS2812 `show()` (bit-banged), 60 pixels | ~1.8 ms, interrupts off |
| Stepper at 3200 steps/s | needs a step every ~300 µs |

The conflict: a stepper stepped from `loop()` will miss steps whenever a strip or full LED refresh blocks longer than the step interval.

## Decisions so far (confirm with the team)

1. One non-blocking `loop()`; **no `delay()` anywhere** except in boot code.
2. Write LEDs only when a value changed, and write one LED's channels in one I2C transaction.
3. Start steppers with `AccelStepper`; move to `IntervalTimer` if timing jitters.
4. Prefer DMA-based strip output if the strip is long.
5. Track the maximum `loop()` duration with `micros()` and expose it (see *Serial Link Performance*) so we can see problems rather than guess.
