# Serial Link Performance: Bandwidth, Latency and Bounds

**Concept:** how to reason about the speed of a communication link, and where the real limits are for the Pi-to-Teensy connection.

**Important:** every number below is an *estimate* from arithmetic and datasheet-style figures. Measure on the real hardware (last section) before relying on any of them.

## The general idea

Two different things are often confused:

- **Bandwidth (throughput):** how much data per second fits through the link.
- **Latency:** how long one message takes from sender to receiver.

A link can have huge bandwidth and still feel slow if something in the chain delays each message. Performance work means finding the *bottleneck*: the slowest stage, not the stage you're most worried about.

## Bandwidth: not our bound

Worst-case traffic with text lines of about 10-25 bytes:

| Source | Rate | Bytes/s |
|---|---|---|
| 2 sliders at 50 Hz | 100 lines/s | ~1.5 KB |
| Button/Hall edges (about 10 presses/s) | ~20 lines/s | ~0.2 KB |
| 10 LED fades at 30 Hz | 300 lines/s | ~6 KB |
| Strip as one fill/effect line at 30 Hz | 30 lines/s | <1 KB |

Total: under 10 KB/s. Teensy 4.1 USB serial runs over a 480 Mbit/s link and can move megabytes per second. We use roughly a thousandth of it.

Parsing a text line on a 600 MHz Teensy takes microseconds, so text parsing cost is also negligible.

## Latency: where the time goes

One button press travelling to the brain:

| Stage | Typical | Notes |
|---|---|---|
| Debounce | ~20 ms | The biggest piece. A *lockout* debounce (report the first edge immediately, ignore bounces for ~20 ms) cuts it to ~0 |
| Teensy loop delay | µs to ms | Set by the longest blocking call (see *Cooperative Loops on a Microcontroller*) |
| USB transmit | small | `Serial.send_now()` forces a partial packet out |
| USB + Linux tty read | ~1 to a few ms | Measure |
| ROS 2 node + executor | ~1 to a few ms | Not real-time; jitter grows under CPU load |
| Brain + audio start | tens of ms | The plan's target is under 200 ms lever pull to first sound |

The serial link is a rounding error next to debounce and the brain.

## The real bounds

1. **Blocking calls inside the Teensy's `loop()`.** I2C writes (~0.3-2.8 ms), bit-banged strip updates (~30 µs per pixel), and stepper timing (a step every ~300 µs at 3200 steps/s) compete for the same loop.
2. **Serial write stalls.** If the Pi stops reading, `Serial.print` on the Teensy can block the loop for tens of milliseconds. Check `availableForWrite()` or drop low-value lines such as slider updates.
3. **Pi jitter.** Linux isn't real-time. The matrix library, audio and video use CPU; the matrix library recommends isolating a core. Run the serial reader on its own thread so executor delays don't back up the port.
4. **Flooding.** A noisy slider or bouncing button can send hundreds of lines/s. Use deadbands, rate limits and debounce at the source.

## Do we need binary encoding?

**No, for this design.** Binary saves bytes we don't need to save, costs debuggability, and forces versioned structs and byte-order care on both sides.

When binary would matter: streaming raw per-pixel strip frames or high-rate analog sampling. Even then, the better fix is usually to **send intent instead of frames** ("rainbow, speed 3"), which keeps traffic tiny and moves real-time work onto the Teensy. If a bulk path is ever needed, add it as a separate command rather than changing the whole protocol.

## Decisions so far (confirm with the team)

1. Text lines, not binary.
2. Report events only on change; rate-limit and deadband the sliders.
3. Consider lockout debounce on buttons to remove ~20 ms.
4. Send animation intent for the strip, not frames.

## How to measure

1. **Round-trip test:** the Pi sends `PING` 1000 times and records round-trip times (p50 and p99). That is the real serial latency.
2. **Loop-time tracker:** the Teensy records the maximum `loop()` duration via `micros()`. A `STATS` command returns it with counts of rejected lines and dropped writes. This shows whether strips, I2C or steppers hurt each other.
3. **Soak test:** run everything at once for the plan's soak-test milestone and watch `STATS`.
