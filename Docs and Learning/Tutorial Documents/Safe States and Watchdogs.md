# Safe States and Watchdogs

**Concept:** how to make a machine with motors, solenoids and actuators fail safely when software crashes, a cable comes out, or power glitches.

## The general idea

Assume things will go wrong: the Pi crashes, USB unplugs, a message is lost. Ask: *what is every output doing at that moment?*

- A **safe state** is the condition each output is put in so nothing can hurt people or hardware: motors stopped, solenoids off, steppers disabled.
- A **watchdog** is a timer that expects regular proof of life. If the proof stops, it forces the safe state.
- **Caps** limit how bad a single command can be, even if the command is wrong.

## Four layers of protection

1. **Safe at boot.** Make every output pin an output and write its off level *first thing* in `setup()`. A floating pin connected to a MOSFET can fire a solenoid at power-up.
2. **Caps in firmware.** Maximum run time (like `MAX_RUN_MS` in `dollar_eater.ino`), maximum solenoid on-time and minimum off-time, maximum step rate. The Pi's request never overrides them.
3. **Host watchdog.** The Teensy records the time of the last valid command from the Pi. If it is older than a timeout, the Teensy runs its own safe-state routine.
   ```cpp
   if (millis() - lastHostMs > HOST_TIMEOUT_MS) allOutputsSafe();
   ```
4. **Explicit `STOP`.** One command that stops everything immediately.

## How this applies to our project

| Output | Hazard | Protection |
|---|---|---|
| Solenoids | Overheat if left on | Max on-time per pulse, minimum off-time |
| DC motors (DRV8871) | Run forever if `STOP` is lost | Every `MOTOR` has a duration; max cap; watchdog |
| Linear actuators (BTS7960) | Drive into the end of travel; both PWMs high | Max run time, never both directions at once |
| Steppers (A4988) | Hold current heats the motor | Shared `EN` disables both when idle |
| Strip and LEDs | Power draw | Brightness limit |

The Pi keeps the watchdog fed with `PING` about every 500 ms when idle; the timeout is about 2 s (both should be named constants).

**Why timed commands are a safety feature, not a policy leak.** `MOTOR id speed ms` carries its own end time. If the Pi dies after sending it, the Teensy still stops the motor on schedule. This is the one kind of decision that belongs on the Teensy (see *Layering the Hardware Interface*).

## Hardware safety (not firmware)

- Common ground between the Teensy and every driver and supply.
- Motors and the strip run from their own supplies, never from Teensy USB.
- On the Teensy 4.1, cut the VUSB-VIN connection (or use a diode) if USB and an external 5 V supply can both be connected.
- Set the A4988 current limit (VREF) before connecting the motor.
- Test drivers unloaded at low speed first.

## Optional extra: Teensy hardware watchdog

The Teensy 4.x has a hardware watchdog timer that can reset the chip if `loop()` itself hangs. That protects against firmware bugs, which the host watchdog does not. It is worth considering once the basic firmware works; check PJRC's forum and the i.MX RT1060 reference manual for the Teensy-specific library or registers.

## Decisions so far (confirm with the team)

1. Safe state first in `setup()`; `STOP` command; caps on every timed output.
2. Host watchdog: `PING` every ~500 ms, timeout ~2 s.
3. Test the watchdog as its own bring-up step by stopping the `PING`s.
