# Project Setup Guide: Simulate on the Mac, Test on the Pi

This guide explains what we need to know to structure the Olin FUN Machine so we can develop and test the logic on our Macs, then run the same code on the Raspberry Pi with real hardware.

Related files: `README.md` (phases), `Project Decisions.md` (Pi 4B 8GB, ROS 2 Lyrical, Docker), `System_Architecture.png` (nodes and topics).

---

## 1. The big idea

```
        Mac (simulation)                         Raspberry Pi (real)
  ┌─────────────────────────┐              ┌─────────────────────────┐
  │ Docker container        │              │ Docker container        │
  │  decision_maker  ◄──────┼─ same code ──┼─► decision_maker        │
  │  sim lever node         │              │  real lever node (GPIO) │
  │  sim display node       │              │  real display node      │
  │  sim voice node         │              │  real voice node (3.5mm)│
  └─────────────────────────┘              └─────────────────────────┘
```

- The **decision maker** and all ROS topics are identical on both machines.
- Only the **component nodes** differ: each has a *simulated* backend and a *hardware* backend.
- A launch argument picks which backend runs. Same image, same code, different launch file.

Why this works: the Mac (Apple Silicon) and the Pi 4B are both **arm64**, so one Docker image runs on both. No cross-compiling or emulation.

## 2. Concepts to learn first

| Concept | What it is | Where we use it |
|---|---|---|
| **ROS 2 node** | A program that publishes/subscribes to topics | Every box in the architecture diagram |
| **Topic** | A named message channel (`Big_Lever_State`) | The arrows in the diagram |
| **Package** | A folder of nodes with a `package.xml` | We group nodes into a few packages |
| **Workspace** | A folder (`src/`) holding packages, built by `colcon` | The root of our code |
| **Launch file** | A Python file that starts many nodes with settings | `sim.launch.py` vs `hw.launch.py` |
| **Docker image/container** | A packaged OS + ROS + deps; a running instance of it | Our dev environment on both machines |
| **Docker Compose** | A YAML file describing how to run containers | One command to start sim or hardware |
| **GPIO** | Pins on the Pi that read/write voltages | Hall-effect sensors, button LEDs |

Good starting point: the official ROS 2 tutorials, "Beginner: CLI tools" and "Beginner: Client libraries" (publisher/subscriber in Python). Do these inside the Docker container once it's working.

## 4. Simulated vs. real: the backend pattern

Each component node has a thin ROS wrapper and a swappable backend. This answers the README's "interface or subclass?" question: use an **abstract base class** (interface) with two subclasses.

```python
from abc import ABC, abstractmethod

class LeverBackend(ABC):
    @abstractmethod
    def read(self) -> bool:
        """True if the lever is in the active position."""

class SimLever(LeverBackend):
    """Value set by a keyboard/web UI or a scripted test."""
    def __init__(self): self.value = False
    def read(self): return self.value

class GpioLever(LeverBackend):
    """Reads the Hall-effect sensor on a GPIO pin."""
    def __init__(self, pin: int):
        from gpiozero import DigitalInputDevice   # import here so the Mac image doesn't need it
        self.dev = DigitalInputDevice(pin)
    def read(self): return bool(self.dev.value)
```

The ROS node picks a backend from a parameter:

```python
backend = self.declare_parameter("backend", "sim").value
self.lever = SimLever() if backend == "sim" else GpioLever(pin=17)
```

Rules that keep this working:
1. **Hardware libraries are imported inside the hardware class**, never at the top of the file.
2. **The decision maker only talks to topics.** It never imports anything from `fun_hardware`.
3. **Debouncing and unit conversion happen in the backend**, so topics carry clean values.
4. **Every real component gets a sim twin.** Add the sim version first. It's how we test the logic.

Per-component backends (from the architecture diagram):

| Node | Sim backend | Hardware backend |
|---|---|---|
| Lever / Falling-off lever | keyboard or web toggle | GPIO read (Hall-effect) |
| Power button | toggle + print LED state | GPIO read + GPIO write (LED) |
| Voice | log the line name (optionally play on Mac speakers) | load audio file, play on 3.5mm output |
| Multi-function button | toggle + print color | GPIO read + RGB LED output |
| Display | write the image to a PNG or show it in a web page | pixel array to display driver |

## 5. Docker setup

### Dockerfile (sketch)

```dockerfile
# Check that this tag exists for arm64 on Docker Hub. Lyrical is a very new release.
# If there is no official image, start from ubuntu and install ROS from the apt repo.
FROM ros:lyrical

RUN apt-get update && apt-get install -y \
    python3-colcon-common-extensions \
    python3-pip \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /ws
```

Install Python deps for hardware (`gpiozero`, `lgpio`) in the same image. They're harmless on the Mac as long as they're only imported by the hardware backends.

### compose.yml (sketch)

```yaml
services:
  sim:
    profiles: ["sim"]
    build: .
    volumes:
      - ../src:/ws/src
    command: bash -lc "colcon build --symlink-install && source install/setup.bash && ros2 launch fun_bringup sim.launch.py"

  hw:
    profiles: ["hw"]
    build: .
    network_mode: host
    devices:
      - /dev/gpiochip0
      - /dev/snd
    volumes:
      - ../src:/ws/src
    command: bash -lc "colcon build --symlink-install && source install/setup.bash && ros2 launch fun_bringup hw.launch.py"
```

`privileged: true` is the quick way to get hardware access while prototyping. Switch to specific `devices:` once things work.

## 6. Mac workflow (simulation)

1. Install Docker Desktop.
2. From the repo:
   ```bash
   docker compose -f docker/compose.yml --profile sim build
   docker compose -f docker/compose.yml --profile sim run --rm sim bash
   ```
3. Inside the container:
   ```bash
   colcon build --symlink-install
   source install/setup.bash
   ros2 launch fun_bringup sim.launch.py
   ros2 topic list
   ros2 topic echo /Big_Lever_State
   ```
4. Edit files on the Mac. Because `src/` is mounted into the container and we build with `--symlink-install`, Python changes take effect on the next launch without a rebuild.

What you **can** test on the Mac: all decision-maker logic, topic wiring, message formats, launch files, timing logic, and unit tests.
What you **can't** test: GPIO, real audio output, the real display, and sensor behavior.

### Testing without hardware
- Unit-test the branching logic as plain Python (no ROS needed).
- Use `launch_testing` or `pytest` to start the sim nodes, publish fake inputs (lever flipped, button pressed), and assert the outputs (voice line published, light on).
- Publish by hand from the CLI:
  ```bash
  ros2 topic pub --once /Big_Lever_State std_msgs/msg/Bool "{data: true}"
  ```

## 7. Pi workflow (real hardware)

### One-time Pi setup
1. Flash a **64-bit** OS with Raspberry Pi Imager (Ubuntu Server or Raspberry Pi OS 64-bit). Set the hostname, username, Wi-Fi, and enable SSH in the imager.
2. SSH in: `ssh <user>@<hostname>.local`
3. Install Docker and let your user run it without sudo:
   ```bash
   curl -fsSL https://get.docker.com | sh
   sudo usermod -aG docker $USER   # log out and back in
   ```
4. Clone the repo: `git clone https://github.com/samjackson24816/Olin-FUN-Machine.git`

### Day-to-day
- **Git route (recommended):** commit and push from the Mac, then on the Pi: `git pull`.
- **Fast iteration:** `rsync -av src/ <user>@<hostname>.local:~/Olin-FUN-Machine/src/`
- **Editing on the Pi directly:** VS Code Remote-SSH.

Run on the Pi:
```bash
docker compose -f docker/compose.yml --profile hw up --build
```

### Bring hardware up one piece at a time
1. Test the raw wiring outside ROS with a few lines of `gpiozero` (does the Hall sensor change when the magnet moves?).
2. Wrap it in the hardware backend and run just that node (`ros2 run fun_hardware lever_node --ros-args -p backend:=gpio`).
3. Confirm the topic with `ros2 topic echo`.
4. Only then add it to `hw.launch.py`.

Mix and match: `hw.launch.py` can run a real lever with a simulated display until the display is wired.

## 8. Gotchas

- **Lyrical image availability.** The official `ros:lyrical-ros-base` tag exists on Docker Hub (checked 2026-10-30). Confirm it pulls on arm64 when you first build. Fall back to Ubuntu plus the ROS apt repo if not.
- **Mac and Pi can't easily share ROS topics.** Docker Desktop on macOS has no real host networking, so ROS 2's default discovery (multicast) won't reach the Pi. Run the whole system on one machine at a time. If we later want the Mac to watch the Pi, look at `rmw_zenoh` or a FastDDS discovery server.
- **GPIO libraries.** Use `gpiozero` with `lgpio` (or `libgpiod`). The old `RPi.GPIO` is unreliable on recent Pi OS versions.
- **Hall-effect sensors** may need pull-up/pull-down resistors and software debouncing.
- **Pin numbers.** Pick BCM numbering and keep all pin assignments in one config file (e.g. `fun_bringup/config/pins.yaml`), not scattered through the code.
- **Audio.** Confirm the 3.5mm jack is selected as the output and that `/dev/snd` is passed into the container.
- **SD card wear and power.** Use a good SD card and a proper 5V 3A supply. Under-voltage causes odd failures.
- **Build artifacts.** Never commit `build/`, `install/`, or `log/`.
- **Pi performance.** Builds are slower on the Pi than on the Mac. Do most development on the Mac and use the Pi to verify.

## 9. Suggested order (maps to README phases)

1. **Phase 1, structure:** Dockerfile, compose file, empty packages, `.gitignore`. Goal: `ros2 topic list` works in the Mac container.
2. **Phase 2, node structure:** define the topics and message types from the diagram, write the abstract backend classes, and write the node skeletons.
3. **Phase 3, simulated implementations:** sim backends, `sim.launch.py`, a way to poke inputs (CLI or web page), and tests for the decision maker.
4. **Phase 4, hardware implementations:** set up the Pi, then add the GPIO/audio/display backends one component at a time and build `hw.launch.py`.

## 10. Open questions for the team

- Python or C++ for the nodes? (Python is faster to iterate on and is what `gpiozero` expects.)
- Which topic message types? `std_msgs` (Bool, String, ColorRGBA) and `sensor_msgs/Image` may be enough, which avoids a custom `fun_interfaces` package.
- What display hardware and driver are we using? This decides how the Display node talks to it.
- Do we want the Pi's web server for feedback and simulation (from `Project Decisions.md`)? If so, it should be another node that only publishes and subscribes topics.
- How do we get the Mac to see the Pi's topics, if we want that at all?
